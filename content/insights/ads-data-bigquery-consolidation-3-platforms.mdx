## なぜ媒体別のレポート画面のままでは 1 枚にならないのか？

<Answer>
  広告データの集約とは、媒体ごとに形の違う日次成果データを 1
  つの共通スキーマへ正規化して BigQuery
  に積み、1 枚のダッシュボードで見る構成を指す。手順は、①共通スキーマ（日付 × 媒体 × キャンペーン ×
  指標）の最小列を決める ②取得経路を媒体ごとに選ぶ（公式 API 直結 / ETL SaaS
  経由） ③日次バッチで直近数日を冪等に上書きする ④媒体で定義の違う指標を集約前に吸収する
  ⑤鮮度と欠損を監視する、の 5 段階。例外として、API の提供が限定的な媒体と、少額で 1
  媒体しか使っていないアカウントは、集約せず管理画面のままでよい。
</Answer>

管理画面を 3 つ開いて数字を手で写す運用が破綻するのは、作業時間よりも定義がそろわないためだ。同じ「コンバージョン」という列名でも、媒体によって計上する日が違い、参照する期間の窓が違い、通貨と時間帯の基準も違う。手で足した合計は、足した人にしか再現できない。集約の目的は見た目を 1 枚にすることではなく、**同じ定義で並べた数字を毎朝同じ手順で再現できる状態を作る**ことにある。以下は当社が 2026 年 4 月から 9 月にかけて実装・運用したダッシュボード基盤の構成を、案件が特定されない形に一般化したものである<Cite n={1}>mixednuts 社内実測、観測期間 2026-04〜2026-09。対象は複数媒体で広告を出す EC 事業者向けの日次ダッシュボード基盤</Cite>。

## 手順 1 — 共通スキーマの最小列を決める

<Principle num="01" heading="最小 9 列から始め、媒体固有の列は後から足す" />

媒体ごとのレポート項目をすべて取り込もうとすると、媒体固有の列が増え続けてスキーマが安定しない。まず全媒体に共通して存在する最小列だけを決め、そこに入らないものは後回しにする。

| 列 | 型 | 役割 |
| --- | --- | --- |
| 日付 | DATE | 分割（パーティション）の基準列 |
| 媒体 | STRING | 媒体の識別子。表記ゆれを 1 つに寄せる |
| アカウント | STRING | 同一媒体で複数口座を持つ場合の区別 |
| キャンペーン ID | STRING | 突合の主キー。名称の変更に強い |
| キャンペーン名 | STRING | 表示用。ID の代わりに使わない |
| 費用 | NUMERIC | 丸め誤差を避けるため浮動小数を使わない |
| 表示回数 | INT64 | — |
| クリック数 | INT64 | — |
| コンバージョン数 | NUMERIC | 媒体側で小数按分されるため整数にしない |

この 9 列に加えて、行を書き込んだ時刻を記録する列を 1 つ持たせると、再取得したときにどの世代のデータかを後から判別できる。テーブルは日付で分割しておくと、クエリが読む範囲が日付で絞られ、費用が想定外に膨らむのを防げる<Cite n={2}>BigQuery 公式ドキュメント「Introduction to partitioned tables」</Cite>。

<PullQuote author="mixednuts 実装ログ">
  スキーマを仕様書から起こすと、実際にデータが流れている媒体と食い違う。列は「既存のパイプラインに実際に流れている値」を一次資料にして決めたほうが後戻りが少ない。
</PullQuote>

## 手順 2 — 取得経路は媒体ごとに選ぶ。直 API と ETL SaaS のどちらを使うか？

<Principle num="02" heading="全媒体を同じ方法でそろえようとしない" />

取得経路は、媒体が公開している公式 API を自分で叩くか、複数媒体をまとめて取ってくる [ETL SaaS](/insights/windsor-vs-supermetrics) を経由するかの 2 種類しかない。どちらかに統一する必要はなく、媒体ごとに違ってよい。

| 媒体 | 取得経路の選択肢 | 反映の速さ | 費用感（相対） | 実装の重さ |
| --- | --- | --- | --- | --- |
| Google 広告 | 公式 API 直結 | 前日分を当日朝に取得できる | 実行環境の費用のみ | 中 |
| Microsoft 広告 | 公式 API 直結 / SaaS 経由 | 直 API は前日分。SaaS 経由は 1〜2 日遅れることがある | SaaS は媒体数によらない月額固定 | 中 |
| Yahoo 広告 | 公式 API 直結 / SaaS 経由 | 同上。SaaS 側の仕様で月次のまとめ取得になる場合がある | 同上 | 中〜高 |

当社は公式 API のライブラリが整っている媒体を自前実装、残りを ETL SaaS 経由という分担で始め、運用が安定した後に一部を直 API へ切り替えた。**最初から全媒体を自前実装すると、集約の設計が正しいかを検証する前に、媒体ごとの認証と仕様差の対応で時間を使い切る。** 判断の目安は、取得したい粒度が SaaS の提供列に収まるか、1〜2 日の遅れが意思決定に影響するか、媒体側の仕様変更に自分で追随し続けられるか、の 3 点である。

## 手順 3 — 日次バッチを冪等にする

<Principle num="03" heading="追記ではなく、直近の窓を削除して入れ直す" />

広告データは確定しない。当日に取得した値は、コンバージョンの後追い計上や無効クリックの調整で数日かけて増えることがある。この性質を無視して日次で追記していくと、テーブルには「取得した日の値」が積み上がり、あとから見た数字が管理画面と合わなくなる。対処は単純で、**毎日、直近数日ぶんを削除してから入れ直す**。当社は直近 14 日を再取得の窓にしている。同じ日に何度実行しても結果が変わらないため、失敗した日の再実行も、遡っての修正も同じ処理で済む。書き込みは 1 行ずつ送らず、まとめて読み込ませる方式を使う。行単位の投入は追加費用がかかるうえ、直後の削除・更新が一定時間できない<Cite n={3}>BigQuery 公式ドキュメント「Batch loading data」</Cite>。

処理の骨格は次の十数行に収まる。

```text
# 日次同期（1 媒体分）
for media in media_list:
    rows = normalise(fetch(media, since=today-14, until=today-1))
    if len(rows) == 0:
        log_run(media, "empty"); continue      # 空なら削除しない
    delete_where(media, today-14 .. today-1)   # 再取得の窓だけ消す
    load(rows)                                 # まとめ書き込み
    log_run(media, "ok", n=len(rows))          # 実行結果を別テーブルへ
```

要点は 3 つ。**取得がゼロ件のときに削除しない**（媒体側の一時的な失敗で既存データが消える）。**媒体ごとに失敗を隔離する**（1 媒体の障害で全媒体が止まらない）。**実行結果を別テーブルに記録する**（監視はこのログがないと成立しない）。

## 手順 4 — 媒体で定義が違う指標をどう吸収するか？

<Principle num="04" heading="定義の差は集約したあとでは戻せない" />

同じ列名で並べた瞬間に、定義の差は見えなくなる。集約する前に、次の 4 点を媒体ごとに確認して記録しておく。

| 論点 | 何が違うか | 集約時の扱い |
| --- | --- | --- |
| コンバージョンの計上日 | クリック日に遡る媒体と、成果発生日に計上する媒体がある | どちらの基準で並べるかを決め、注記に残す |
| 参照期間の窓         | 成果として数える期間の長さが媒体・目標ごとに違う   | 窓が短い媒体は遅れた成果を取りこぼす前提で読む |
| 通貨と換算           | 口座の通貨設定と、出力時の換算基準                 | 保存は口座通貨のまま、換算は表示側で行う |
| 時間帯               | 口座に設定された時間帯で日付が切られる             | 日付の境界がずれる媒体を明示する |

とくに参照期間の窓は見落としやすい。検討期間の長い商材で窓が短く設定されていると、その媒体だけ成果が構造的に少なく出る。媒体間の効率を横並びで比べる前に、窓の設定を突き合わせる。

集約したデータをサイト側の計測と突き合わせる場合は、**キャンペーンを一致させる識別子が媒体ごとに違う**点も効く。当社の実測では、自動タグ付けが有効な媒体は数値 ID で照合できた一方、手動でパラメータを付与している媒体は、キャンペーン名を変更した時点で照合が切れた。名称ではなく ID で突き合わせる設計にしておくとよい。

## 手順 5 — 鮮度と欠損をどう監視するか？

<Principle num="05" heading="ジョブが動いたかではなく、データの最終日を見る" />

同期が止まったことに気づく経路は、実行ログを見る方法とデータの最終日を見る方法の 2 つがある。前者だけでは足りない。ジョブが成功で終わっていても、媒体側が空の結果を返していればデータは増えていない。当社は一度、更新されない原因を障害探しの方向だけで調べて実行ログばかりを追ったが、実際には実行環境が移行で止まっていた媒体と、配信を停止していて正常にデータが無い媒体とが混在していた。**「ジョブが走ったか」と「データの最終日はいつか」は別の問い**で、後者を見ないと正常な運用理由を障害として扱う。

監視項目は 4 つで足りる。媒体ごとのデータ最終日と当日との差、直近 7 日の日次行数の急変、実行ログの連続失敗、再取得の窓の外で値が変わっていないかの確認。いずれもダッシュボードとは別系統で通知する。画面の中に警告を出す設計にすると、開かない日は気づけない。

## 経路を切り替えるとき、新旧の突合で何を見るか？

経路を替えるときは、**新旧を並行させて突き合わせてから切り替える**。当社は切替前に 7 日ぶんを両経路で取得し、日次の費用の乖離が ±1% 以内であることを合格基準とした<Cite n={1}>mixednuts 社内実測（観測期間 2026-04〜2026-09）</Cite>。

観測されたことが 2 つある。1 つは、**費用の合計が完全に一致していても行数は一致しないことがある**点だ。SaaS 経由の行に、同一の日付・キャンペーン・広告グループの組み合わせが重複して入っているケースがあり、直 API 経由では重複が解消された。合計だけを見ていると重複に気づけない。もう 1 つは、コンバージョン数が新経路のほうが数件多く出る点で、これは差異ではなく計上の遅れである。**費用は一致を求め、コンバージョンは方向と差の大きさを見る**と基準を分けておくとよい。

| 突合項目 | 合格基準 | 不一致だったときの解釈 |
| --- | --- | --- |
| 日次の費用 | 乖離 ±1% 以内 | 取得範囲・時間帯・通貨のいずれかがずれている |
| 行数 | 一致しなくてよい | 重複行の有無を主キーで確認する |
| コンバージョン数 | 新経路が同数か数件多い | 計上の遅れ。旧経路の値が古い |

切替後も旧経路は一定期間残す。止めた後に不足が判明すると、その期間のデータは取り直せないことがある。

## どこまでやらなくてよいか — 集約しない方がよい場合

例外は 2 つある。レポート API の提供が限定的な媒体は、取得できる粒度が管理画面より粗い、または遡及取得に制約があるため、集約に無理に載せず管理画面の値を注記する形にしたほうが早い。出稿が 1 媒体に集中していて金額も小さいアカウントも、集約の設計と保守にかかる時間が得られる示唆を上回る。

費用面では、日付で分割したテーブルと日付で絞ったクエリを守れば、保管とクエリの費用そのものは大きくならず、当社の構成では月額 10 ドル未満の水準に収まっている<Cite n={1}>mixednuts 社内実測（観測期間 2026-04〜2026-09）。データ量に依存するため他の構成へ一般化できる値ではない</Cite>。増えるのは費用ではなく、媒体仕様の変更に追随する保守の時間である。

## 次に読む診断チェック — 集約基盤を作る前に 6 項目を確認する

着手前に次の 6 項目を確認すると、作り直しのほとんどは避けられる。

1. 共通スキーマの最小列を決め、媒体固有の列を後回しにする合意ができているか。
2. 媒体ごとの取得経路を、鮮度・粒度・保守負担の 3 点で選び分けたか。
3. 日次バッチは同じ日に何度実行しても結果が変わらないか。再取得の窓を何日にするか決めたか。
4. コンバージョンの計上日・参照期間の窓・通貨・時間帯を媒体ごとに記録したか。
5. データの最終日を、実行ログとは別に監視しているか。
6. 経路を切り替える際の突合基準を、切り替える前に決めたか。

1 つでも未確定なら、画面設計より先にそこを埋めたほうがよい。mixednuts では、こうした広告データ基盤の設計と実装を <ServiceLink href="/services/marketing">マーケティング支援</ServiceLink> の一部として提供している。

## FAQ

**Q. まず BI ツールを選ぶべきか、先にデータ基盤を作るべきか？**
A. 先に共通スキーマとデータの置き場を決める。表示ツールは後から差し替えられるが、定義の異なるデータを取り込んだ後の作り直しは全期間の再取得を伴う。

**Q. 全媒体を公式 API で自前実装したほうがよいか？**
A. 媒体側の仕様変更に追随し続けられるかで決める。追随の担当を置けないなら、ETL SaaS 経由のほうが総保守時間は短い。当社は SaaS 経由で先に 1 枚を成立させ、運用が安定した媒体から順に直 API へ切り替えた。

**Q. 日次バッチで何日ぶんを取り直せばよいか？**
A. 媒体の成果計上が確定するまでの日数より長く取る。当社は直近 14 日を窓にしている。窓を短くすると遅れて計上された成果を取りこぼし、長くすると毎日の処理量が増えるため、実際の遅延分布を見て決める。

**Q. 媒体側の数字とダッシュボードの数字が合わないときは何から見るか？**
A. ①比較している期間と時間帯の基準 ②コンバージョンの計上日と参照期間の窓 ③取得の窓の外に古い値が残っていないか ④重複行の有無、の順で確認する。合計だけでなく主キー単位の行数も見る。

**Q. ダッシュボードが更新されていないことに、どうすれば早く気づけるか？**
A. 媒体ごとのデータ最終日を毎日チェックし、当日との差が想定を超えたら通知する。実行ログの成功・失敗だけでは、空の結果を返して成功したケースを検出できない。
