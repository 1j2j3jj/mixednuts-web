## なぜ「書いてあるルール」は破られるのか

<Answer>
  自律 AI
  エージェントに対する運用ルールは、プロンプトやドキュメントに書いただけでは実行されない。読むかどうか・従うかどうかがセッション自身の自己申告に依存する層に置かれている限り、同じ失敗は再発する。対策は、ルールの重要度と実害の大きさに応じて「散文
  → hook 注入 →
  機械ゲート」へ段階的に強制力を上げる体系を組織として持つことだった。
</Answer>

mixednuts は 2026 年 7 月、自社の全運用ルール文書（80 本超）を棚卸しした。結果、実害や再発を記録した学習の大半が「必要時参照の散文」——つまり、そのルールを読むかどうか・思い出すかどうかがエージェント自身のセッション判断に委ねられている層に置かれていることが分かった。これは「決めたことが実行されない」構造の主因と一致した。散文で書かれたルールは、書いた瞬間は正しくても、次のセッションが読むという保証がない。

## L1〜L6 の強制レベル体系

そこで導入したのが、ルールごとに強制レベルを明示する体系だ。L1 は必要時にだけ参照される散文、L2 は毎回のセッション起動時に読み込まれる常時ロードの散文、L3 は成果物の提出そのものが手続きとして必須になっているもの、L4 は hook によるプロンプト注入（作業の節目で自動的にルールを思い出させる）、L5 は独立した検証者（別のエージェントが生成物を批評する）、L6 は lint・exit コード・パーミッション・hook ブロックといった機械ゲートで、そもそも違反した操作自体が実行できない層だ。

<Principle num="01" heading="散文は解釈され、コードは実行される" />

同じ内容のルールでも、散文として書かれている限り「今回は例外だろう」という解釈の余地が残る。機械ゲートまで昇格させたルールは、解釈の余地なく実行前に止まる。この違いは、同一の失敗パターンが散文のままだと繰り返し発生し、機械ゲート化した瞬間に発生しなくなるという形で実証された。

## 散文が hook になるまでに、なぜ 2 回の再発を要するのか

すべてのルールをいきなり機械ゲートにはできない。機械化にはコストがあり、誤検知（本来許可すべき操作を誤ってブロックする）のリスクも伴う。mixednuts の運用では、「同種の問題が 2 回発生した場合、または実害が一定額を超えた場合は L4 以上への昇格を既定とする」という基準を置いている。1 回目の失敗は個別の判断ミスとして散文で注意喚起するが、2 回目が発生した時点で、それは個別のミスではなく構造的に再発する類型だと判断し、hook 化の検討を義務づける。

実例として、実行タスクの中で使用するモデルの指定漏れによるコスト超過は、CLAUDE.md への明記だけでは止まらず 2 回再発し、その後 hook による機械チェックを配線して初めて再発が止まった。破壊的な git 操作のブロックも同様に、単純な禁止事項の明記だけでは迂回パターンが見つかり、機械的な検知ロジックの強化を経てようやく実効性を持った。

| 強制レベル | 内容                 | 実行されるまでの依存先                       |
| ---------- | -------------------- | -------------------------------------------- |
| L1         | 必要時参照の散文     | セッションが自発的に思い出すこと             |
| L2         | 常時ロードの散文     | 毎回読み込まれるが解釈の余地が残る           |
| L3         | 成果物必須の手続き   | 提出物の有無で間接的に検証                   |
| L4         | hook・プロンプト注入 | 節目で自動的に思い出させる（警告止まり）     |
| L5         | 独立検証者           | 別エージェントによる批評（見落としの可能性） |
| L6         | 機械ゲート           | 違反操作自体が実行できない（最も強い）       |

<PullQuote author="mixednuts ルール運用メモ">
  再発1回目は個人の判断ミス、2回目は構造の欠陥。構造の欠陥を散文の追記で埋め続けると、ルール文書は増えるのに実効性は上がらない。
</PullQuote>

## ルール層そのものを書き換える権限は誰にあるか

強制レベルを上げていく過程で、もう一つの問題に直面した。ルールを機械ゲート化する作業自体が、AI エージェントによる自己判断で行われてしまうと、「エージェントが自分自身への制約を自分で緩めることもできる」という循環が生まれる。これを防ぐため、mixednuts はルール層（組織の行動規範を定義する文書群）の書き換えに、金銭操作や破壊的な git 操作と同格の**CEO 明示同意ゲート**を設けた。提案は BLUF・差分・理由・影響範囲を提示したうえで、CEO の明示的な同意を得てから初めて編集・コミットできる。夜間の自律実行など、その場で同意が取れない場合はルール層を編集せず、承認待ちのキューに積んで次の対話セッションの冒頭で提示する運用にしている。

## FAQ

**Q. すべてのルールを最初から機械ゲート（L6）にしないのはなぜか？**
A. 機械化にはコストと誤検知リスクが伴う。誤って正当な操作までブロックすると、別の形で業務が止まる。実害と再発頻度で優先順位をつけ、必要なものから昇格させる方が持続可能だと判断している。

**Q. hook によるプロンプト注入（L4）はどの程度の効果があるのか？**
A. 完全な防止ではなく警告にとどまる。ただし、節目で自動的に注意喚起されることで、セッションが自発的に思い出すことに依存するより再発率は下がる。L6 のような実行ブロックには及ばない中間層という位置づけだ。

**Q. ルール層の書き換えに CEO 同意を必須にすると、対応が遅くならないか？**
A. 遅くなる場面はある。ただし、ルール層は組織の行動規範そのものであり、誤った書き換えの影響範囲は個別タスクより大きい。同意ゲートは速度より安全を優先する設計判断だ。

**Q. 機械ゲート化した後、ルールの陳腐化にはどう対応するのか？**
A. 正本文書には四半期ごとの棚卸しを設け、参照切れや矛盾が無いかを確認する運用にしている。機械ゲートも前提が変われば無効化や更新が必要になる。

**Q. この体系は AI エージェント組織以外にも応用できるか？**
A. できる。人間の組織でも「規程に書いてあるが守られない」問題は同型で起きる。強制レベルを可視化し、再発した規程から優先的にシステム化・自動チェック化するという発想はそのまま転用できる。

**Q. 強制レベルを上げる判断は誰が最終決定するのか？**
A. 機械化の実装自体は担当エージェントが行うが、どのルールをどのレベルまで上げるかという方針判断は、影響範囲を明示したうえで人間（CEO）が最終確認する運用にしている。
